Executive summary

Product

Fryyday is a safety-first, activity-first social app that solves a specific failure: adults have contacts but no plans. Dating apps optimise for matching. Messaging apps optimise for talking. Fryyday optimises for actually showing up somewhere.

A user opens the app, sees real plans happening near them this week — a 7am walk, coffee at 4, pickleball on Sunday — asks to join one, the host accepts, a chat opens, they meet in a public place, and both confirm it happened. That last confirmation is the only metric that matters.

What changes in v2.0

v1 was a single-device demo: beautiful, 117 tests green, an installable APK — and fundamentally a simulation. There was no server. The other person was a Timer. Closing the app lost everything. v2.0 makes it real.

The honest cost of the stack switch

React Native was directed, so React Native it is — but the price should be visible. Around 9,000 lines of working Dart (86 files, 117 passing tests, a full design system, 22 screens, a tested invitation engine) do not port automatically. Roughly 3 of the 14 weeks below is re-implementing UI that already existed.

Why React Native is nonetheless defensible here

One language from the Postgres query to the button label, a shared contracts package that makes client/server type drift impossible, over-the-air updates for instant hotfixes without app-store review, and a far larger hiring pool in India. That shared-types property is the single biggest lever on the "no errors" requirement — and Flutter cannot offer it.

Three requirements, made concrete

RequirementHow it is delivered
"No errors"A 7-layer error-elimination strategy (§11): TypeScript strict, one Zod schema per API shape shared by client and server, runtime validation at every boundary, database constraints as the final backstop, blocking CI gates, error boundaries, Sentry on both tiers — plus a Definition of Done no PR merges without.
"Deploy on AWS faster"The entire cloud is one cdk deploy (§13). Infrastructure is code, reviewed in PRs, reproducible across three environments. First deploy ≈ 25 minutes; every deploy after ≈ 6 minutes, zero-downtime, automatic rollback on failed health checks.
"Designed correctly"The design system is tokens in code, not a PDF (§5). Every screen has acceptance criteria, every state is specified, and accessibility is a merge gate rather than a cleanup phase.

The product

ProductBackend

Problem. Between 22 and 35 the social defaults break. College ends, people move cities, work goes remote. You still have a contact list — you just have nothing on the calendar. Existing products make this worse: they hand you infinite strangers to talk to and no reason to leave the house, and the moment you try to meet someone the experience feels unsafe or spammy.

User. 22–35, living in Bangalore, new to the city, newly remote, or recently out of college. Disposable time on weekday evenings and weekends. Used to verification friction.

Promise. "Something real to show up to this week, with people you can trust."

The core loop

Everything in the app exists to move a user one step further around this loop. A feature that does not serve the loop does not ship.

01Create a plan
02Nearby people discover it
03Request to join
04Host decides
05Chat unlocks
06Meet at a public venue
07Both confirm + rate
08Trust score rises

Step 08 feeds back into step 02 — trust compounds discovery

The five safety invariants

These are the product. In v1, three of four were enforced only on the client, which made them decorative — a patched client could bypass every one. In v2.0 all five are enforced server-side, and each has a named test that fails the build if broken.

Enforced in code · not in copy

I1

Accept-before-chat

Nobody can message you until you accepted them. Requesting is never enough. A ChatGuard verifies an accepted row in plan_members before any send is accepted on the socket or REST. → i1-accept-before-chat.e2e.ts
I2

Verified-first

Identity verification gates hosting and 1:1 Find; trust is visible on every profile. A @RequiresVerification() guard sits on POST /plans and POST /finds. → i2-verification-gate.e2e.ts
I3

Public venues by default

venue_public defaults true; private venues require an explicit confirm and are excluded from Discover. → i3-public-venue.e2e.ts
I4

Consent is revocable and cheap

Block, report, quiet hours and women-only plans are one tap and always reachable. Blocks are bidirectional and filtered in the SQL layer of every listing query, not in the app. → i4-block-is-bidirectional.e2e.ts
I5

No silent location leakage NEW

Exact coordinates never leave the server for another user. The API returns a jittered, bucketed distance band — "1–2 km" — never another person's raw lat/lng. Enforced by a serialiser that has no field for it. → i5-no-raw-coords.e2e.ts
Why I5 is new and non-negotiable

The moment there is a real network, "show me who is nearby" becomes "let me triangulate where she lives". A response object that cannot represent another user's exact position is the only defence that survives a hostile client.

The two connection paths

There are exactly two ways two people end up together, and they must never be conflated.

Path A — the Plan path (scheduled · group · public). Someone hosts an activity at a time and place; others ask to join. Create → Feed/Map → Detail → Request → Accept → Chat → Meet → Confirm + rate.

Path B — the Find path (spontaneous · 1:1 · expires in 24h). You are out right now; so is someone nearby. Discover → Find → they accept → a 24-hour group forms with a live countdown → it expires and disappears.

The Find path exists because the Plan path is too slow for "I'm free now". The 24-hour expiry is the safety mechanism, not a limitation: a spontaneous connection must not silently become a permanent channel. Expiry runs as a server-side job, never on the client — an expiry a user can dodge by changing their phone clock is not a safety mechanism.

Explicit non-goals

These are not "later" — they are refusals, and every one protects the loop.

UI/UXReact Native

The aesthetic survives the stack change unchanged: dark glassmorphism × high-contrast cyberpunk. A total-black canvas, one electric neon accent used with discipline, frosted glass surfaces, and glow instead of drop shadows. This page is rendered in it.

Tokens are the only source of truth

No component may declare a raw hex value — an ESLint rule blocks it at review time. Type: Hanken Grotesk for display and body, JetBrains Mono for labels and data. Fonts are bundled, not fetched — a social app that shows a system-font flash on cold start looks broken.

Why this is now cheap in React Native

RN 0.76+ supports boxShadow and filter: blur() on both iOS and Android. Before that, this design system needed per-platform hacks and nine-patch images on Android. Glass uses expo-blur's native BlurView.

Budget: max 3 concurrent BlurViews per screen. Blur is GPU-expensive on mid-range Android — this is the number-one jank risk in the app.

The signature screen — Home / "Launch Pad"

A 6×6 activity masonry over the atmospheric void, plus the command bar. This is the app's identity. Tapping a tile opens Create Plan pre-filled with that activity.

The command bar — Friends ▾ · + · "INVITE NOW / ASK ANYTHING" · ➤ — is the "create a plan in under 60 seconds" promise, and the most important control in the product.

Accessibility is a merge gate, not a phase

Neon-on-black is beautiful and accessibility-hostile if done carelessly.

  • Contrast. Body #E3E2E7 on black = 15.9:1. Secondary #C7C9AB = 11.6:1. Neon on black = 18.9:1. But #919378 = 6.4:1 — permitted for ≥14px only, never body text.
  • Never colour alone. Status is colour + icon + mono label (● VERIFIED, ✕ DECLINED). Roughly 8% of men have colour-vision deficiency and our accept/decline pair is green/red.
  • Touch targets ≥ 44×44 pt, verified by a test that walks the render tree.
  • Every interactive element carries accessibilityLabel, accessibilityRole, accessibilityState. VoiceOver and TalkBack are tested on the core loop each release.
  • Respect reduced motion. The sonar sweep, shimmer and staggered reveals become instant state changes.
  • Dynamic Type to 200%. No fixed-height text containers — the number-one source of clipped text.

Motion

Two to three meaningful animations per key screen, never more. Everything runs on the UI thread via Reanimated worklets — a dropped frame on the neon shimmer makes the whole app feel cheap.

The most important directory in the repo

packages/contracts holds one Zod schema per API shape. The server validates requests with it; the client infers its TypeScript types from it. A backend change that breaks the app fails pnpm typecheck in CI before it can merge. That is how "no errors" is achieved structurally, rather than by testing harder.

The one state rule

Server state lives in TanStack Query and only there. Zustand holds session and ephemeral UI. Socket events do not write data — they invalidate query keys, and the refetch is the single source of truth. This makes "accept a request and watch the member count update everywhere" work by construction rather than by manual synchronisation.

Offline is a requirement, not a nicety

Users open this app on the move, on Indian mobile data, in basements and metros.

  • The query cache persists to MMKV — the app opens with the last-known feed, chat and profile.
  • Mutations queue while offline and flush on reconnect.
  • Chat messages show a pending tick, then sent. Never silently dropped.
  • A global banner states connection status; it is never a full-screen block.
  • On reconnect the socket replays messages missed since the last received seq per room.

The regulatory landmine — start this in week 1

Amazon SNS cannot deliver SMS to Indian numbers without TRAI DLT registration — you register the entity, the sender ID, and every message template. That is a 1–3 week external process, and it has blocked more launches than any technical problem on this page.

Until it clears, use MSG91 or Twilio Verify — both already DLT-registered and able to send on day one. The transport sits behind an OtpTransport interface, so swapping it later is a one-line change.

Session handling

  • Access token: JWT, 15 minutes, verified locally against cached Cognito JWKS — no network hop per request.
  • Refresh token: 30 days, rotating, single-use, stored hashed in Postgres so it can be revoked.
  • Both live in expo-secure-store — Keychain and Android Keystore. Never AsyncStorage.
  • Rate limits: OTP request 3/hour/phone, 10/hour/IP. Verify 5 attempts → 15-minute lock.

One response envelope

Every response uses the same shape, so the client has exactly one error path to handle.

// success
{ "data": { … }, "meta": { "requestId": "01J…", "cursor": "eyJ…" } }

// failure
{ "error": { "code": "PLAN_FULL",
            "message": "This plan is already full.",
            "details": { "planId": "…" },
            "requestId": "01J…" } }

code is a closed TypeScript union in packages/contracts. The client switches on it exhaustively — adding a server error code without handling it client-side fails the build.

Cross-cutting API rules

  • Cursor pagination only — never offset, which skips rows under concurrent inserts.
  • Idempotency-Key header required on every mutating POST, stored 24 hours.
  • Optimistic concurrency via If-Match on plan edits.
  • Per-user and per-IP rate limits in Redis.

Realtime

A Socket.IO gateway on the same Fargate service, transports: ['websocket'] only — skipping the polling fallback means the load balancer needs no sticky sessions, and the Redis adapter handles cross-task fan-out.

The JWT is verified in the handshake and the connection is bound to a userId server-side. Room joins are authorised against the database: a client asking to join a plan room it is not an accepted member of is refused. I1 is enforced here too, not only on REST.

Push notifications

Push is the single largest irritation vector in a social app, so it is throttled by design: a hard cap of 5 pushes per user per day, quiet hours honoured server-side (the job checks, never the device), every category individually opt-out, every push deep-linking to the exact screen — and no growth or marketing pushes in v1.0. Not one.

Identity verification

v1's "verification" was a 2.2-second animation. A trust badge that is not earned is worse than no badge, because it launders risk. v2.0 uses AWS Rekognition Face Liveness — native to the stack, returns a confidence score and reference image. Selfie-only is the right v1 bar: it proves a live human without collecting government ID. Below threshold goes to manual review. Fail closed, never open.

Domain logic

BackendProduct

Pure TypeScript, zero I/O, 100% unit-tested. Ported from the v1 Dart engines, which were correct and well-tested — this is the part of v1 with the most value. It runs on the server; the client never decides eligibility, cost or trust.

Hard gates — run at every tier, never overridden

A candidate is excluded if any is true: is self · blocked in either direction · already a member · plan is full · plan expired · outside the radius · location unknown or stale · women-only mismatch · receiver in quiet hours · receiver hit their daily cap · declined this host within the 7-day cooldown.

These run as SQL WHERE clauses, not application filters, so no code path can forget them.

Discovery ordering — ship the deterministic sort

Tier 1 is soonest (default) or nearest. Spam is impossible by construction, and users can predict the result — which matters more than relevance at low liquidity.

Tier 3 — the weighted ranking — is built and parked:

score = w₁·proximity + w₂·interestOverlap + w₃·reputation + w₄·availability
        − w₅·inviteFatigue − w₆·declineHistory      // all normalised to [0,1]
Turn it on only when there is data to fit it

Enable it behind a flag that A/B tests against Tier 1. If it does not beat the deterministic sort on invite→join conversion, it stays off. Sophistication before liquidity is the classic way to lose a year.

Trust score

trust = bayesianStars(rating, count, prior = 3.5, m = 10) · 0.6
      + reliability(shownUp / committed)                  · 0.4
      − noShowPenalty(noShows)

The Bayesian shrink is what makes it honest: a single 5.0 ranks below a dense 4.8. New users start at the prior, not at zero — otherwise nobody can ever get their first plan.

Invite credits — an anti-spam budget, not a paywall

Reach is scarce so that unwanted contact is structurally rare. Three free credits are granted daily at 00:00 IST, once per calendar day, enforced by a unique index. Spending is a single Postgres transaction — UPDATE … WHERE credits >= cost plus a ledger insert, with a CHECK (credits >= 0) constraint as the final backstop.

The balance always equals the sum of the ledger, asserted by a nightly reconciliation job that pages on mismatch.

Business rules — each one an enforced test

  1. Idempotent join — one request per (plan, user).
  2. One live invite per (plan, person) per sender.
  3. Credits atomic, never negative, every movement ledgered.
  4. Daily credits once per calendar day.
  5. Ratings once per (plan, person), clamped 1–5, only after attendance.
  6. Attendance confirmed once; increments plans_completed.
  7. Blocking is idempotent, reversible, and bidirectional in visibility.
  8. Full plans reject new members even on an accepted request.
  9. Chat membership is created on acceptance, never before (I1).
  10. Finds deduped per person; blocked when an active group already exists.
  11. Cancelling a plan notifies every member and refunds spent credits.
  12. A plan may not be edited after it starts.

Data model

Backend

PostgreSQL 16 + PostGIS 3.4. The full schema is in the repository; what follows is the part that carries the invariants.

-- membership == chat access. I1 lives in this table.
CREATE TABLE plan_members (
  plan_id   UUID NOT NULL REFERENCES plans(id) ON DELETE CASCADE,
  user_id   UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  role      TEXT NOT NULL DEFAULT 'member',
  joined_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  attended  BOOLEAN,
  PRIMARY KEY (plan_id, user_id)
);

CREATE TABLE join_requests (
  id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  plan_id  UUID NOT NULL REFERENCES plans(id) ON DELETE CASCADE,
  user_id  UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  status   request_status_t NOT NULL DEFAULT 'pending',
  UNIQUE (plan_id, user_id)          -- business rule #1, in the schema
);

-- business rule #4: daily credits, once per calendar day
CREATE UNIQUE INDEX idx_ledger_daily
  ON credit_ledger (user_id, (created_at AT TIME ZONE 'Asia/Kolkata')::date)
  WHERE reason = 'daily_grant';

-- business rule #5: one rating per pair, per plan
CREATE TABLE ratings (
  plan_id  UUID REFERENCES plans(id) ON DELETE CASCADE,
  rater_id UUID REFERENCES users(id) ON DELETE CASCADE,
  ratee_id UUID REFERENCES users(id) ON DELETE CASCADE,
  stars    SMALLINT NOT NULL CHECK (stars BETWEEN 1 AND 5),
  PRIMARY KEY (plan_id, rater_id, ratee_id)
);
Read those unique indexes again

Business rules 1, 4 and 5 are enforced by the database, not by application code. Application logic can be bypassed by a race, a retry or a bug. A unique index cannot. Put every invariant you can into the schema.

The core spatial query

SELECT p.id, p.title, p.starts_at, p.member_count, p.max_size,
       ROUND((ST_Distance(p.location, $1::geography) / 1000)::numeric, 1) AS distance_km
FROM plans p
JOIN users h ON h.id = p.host_id
WHERE p.status = 'open'
  AND p.starts_at > now()
  AND ST_DWithin(p.location, $1::geography, $2)         -- metres; uses the GIST index
  AND NOT EXISTS (SELECT 1 FROM blocks b                -- I4, bidirectional, in SQL
                  WHERE (b.blocker_id = $3 AND b.blocked_id = p.host_id)
                     OR (b.blocker_id = p.host_id AND b.blocked_id = $3))
  AND (p.join_rule <> 'women_only' OR $4::gender_t = 'woman')  -- hard gate, in SQL
ORDER BY p.starts_at ASC
LIMIT $5;
The one detail that decides this query's fate

ST_DWithin — not ST_Distance < x — is the whole trick. Only ST_DWithin can use the GIST index. The wrong form is a sequential scan over every plan, and that is the difference between 8 milliseconds and 4 seconds.

Location privacy — how I5 is implemented

  1. Exact coordinates are stored, and used only inside SQL predicates.
  2. The API returns a band: <1 km, 1–2 km, 2–5 km, 5–10 km, 10 km+.
  3. Each user gets a stable random offset seeded from their id (100–300m), so repeated queries from different points cannot triangulate them.
  4. UserPublicDto has no coordinate field at all. It cannot leak by accident, because there is no field to populate.
  5. Updates throttled to one per 5 minutes, foreground only. No background location tracking in v1.0 — the trust cost is not worth the feature.

"No errors" — seven layers

QualityBackendReact Native

This was the most-repeated requirement, so it gets a strategy rather than a promise. Bug-free software is not achieved by testing harder — it is achieved by making broken states unrepresentable. Seven layers, cheapest first.

The compilerstrict: true, plus noUncheckedIndexedAccess, exactOptionalPropertyTypes, noFallthroughCasesInSwitch. any is banned by lint. Discriminated unions and never-exhaustive switches mean adding a new status forces every consumer to handle it.
Shared contracts — the big oneOne Zod schema per API shape. The server validates with it; the client infers types from it. A backend change that breaks the app fails typecheck before merge. This single decision eliminates the most common class of production bug in mobile apps: client/server drift.
Runtime validation at every boundaryNothing is trusted — HTTP bodies, socket payloads, push payloads, deep links, and environment variables. Env vars are Zod-parsed at boot, so the process refuses to start if one is missing rather than failing at 3am on the first request.
Database constraintsNOT NULL, CHECK, FOREIGN KEY and the unique indexes above. The last line of defence, and the only one a race condition cannot beat.
Automated testsUnit (Vitest, ≥90% on domain) · integration against a real Postgres+PostGIS via Testcontainers · contract diffing · five named invariant tests for I1–I5 that cannot be skipped · component tests across all states · Maestro E2E on real iOS and Android · k6 load at 500 concurrent.
Runtime resilienceError boundaries per navigator stack, so one screen crashing never white-screens the app. Typed error envelope with exhaustive handling · retry with exponential backoff · circuit breakers on external providers · graceful degradation (no GPS → city-level feed; no socket → polling) · Sentry on both tiers with source maps uploaded by CI.
Definition of DoneThe checklist below. No PR merges unless every box is ticked. This is the layer that actually prevents the mess, because it runs on every change rather than at the end.

Definition of Done

  • pnpm typecheck clean · pnpm lint clean · pnpm test green
  • All five UI states implemented — loading, empty, error, offline, success
  • Accessibility: labels, roles, ≥44pt targets, contrast verified
  • Loading skeletons — no bare spinners
  • Errors are human-readable and actionable, never a raw code
  • Works offline, or degrades explicitly
  • No hardcoded colours, strings or URLs
  • New endpoint → contract schema + integration test + OpenAPI entry
  • Database change → a reversible migration, tested up and down
  • Touches an invariant → the matching E2E test updated
  • Tested on a physical low-end Android, not just a simulator
  • No console.log, no commented-out code, no TODO without a ticket

AWS & deployment

Cloud
The cost trap nobody warns you about

A NAT Gateway is ~$32/month plus data processing — by far the largest fixed line item in a small AWS account. Avoid it entirely: put VPC endpoints for ECR, S3 (gateway, free), Secrets Manager, CloudWatch Logs and KMS in the private subnets.

Fargate then pulls images and writes logs with no NAT at all. This one decision cuts the monthly bill by roughly a third.

Why Fargate, and not Lambda

DimensionFargate ✓Lambda ✕
WebSocketsNative, long-lived, cheapNeeds API Gateway WS + a DynamoDB connection table
Cold startsNone200–900ms on a p99 request — unacceptable for chat
DB connectionsA normal poolNeeds RDS Proxy or you exhaust connections under load
Local devThe identical Docker imageEmulated, always subtly different
Cost at 5k DAU~$45/mo, predictableCheaper idle, spikier, harder to forecast

Chat is the deciding factor. A realtime app wants a warm, connection-holding process.

Deploy safety

The ECS deployment circuit breaker gives automatic rollback. New tasks must pass /health/deep — which checks database, Redis and Cognito reachability — before the load balancer shifts traffic. A bad deploy rolls itself back in about 90 seconds, without paging anyone.

CI/CD

On PR: typecheck → lint → unit → integration → build both apps → invariant tests I1–I5. All blocking. On merge: image to ECR tagged with the commit SHA → deploy staging → smoke tests → manual approval → deploy prod → Sentry release + source maps. Mobile: EAS build on a version tag, then submit to both stores.

Over-the-air updates, and their hard boundary

eas update ships any JavaScript or asset change in minutes instead of a 24–48 hour review. It cannot change native code — a new module, a permission, an SDK bump — which still needs a store build. Both stores permit OTA for bug fixes; do not use it to ship features that materially change what was reviewed.

Never log PII

Every log line is JSON with traceId, userId, route, durationMs. Never phone numbers, exact coordinates, message bodies or OTP codes — and a CI lint rule greps for those field names inside log calls.
